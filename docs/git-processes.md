# Git 超时与异常进程（开发版）

当前源码构建的桌面、VS Code 和 DSH 使用有时限的 Git CLI 执行器。旧安装包不会自动获得更新。

## 等待与失败

| 路径 | 每条 Git 命令的时限 |
|---|---|
| 插件普通读取、分页、搜索和非提交命令 | 30 秒 |
| 插件提交（包括恢复后的提交） | 120 秒 |
| 桌面地图分页、搜索 | 30 秒 |
| 桌面操作模块的检查和写入命令 | 120 秒 |

这些是单条命令的时限，整个操作可能包含多条命令。清理另有短暂等待：插件最多额外 6.5 秒；桌面终止进程树最多 5 秒，再等待输出关闭最多 2 秒。主进程退出后，输出管道仍受时限约束。

启动失败、非零退出、超时、输出超限会报告错误。普通 stdout/stderr 各最多保留 32 MiB，超出后不能当作完整结果使用；历史搜索流式处理，不一次保留全历史，单字段另有限制。这个限制不等于提交数量上限。二进制读取保持二进制数据。

超时或超限后，程序尝试结束本次 Git 及其子进程，等待退出和输出关闭，再返回。不会自动撤销已经写入的文件、暂存内容、分支或提交；应先检查实际 HEAD、Git 状态和“操作记录与恢复”。提交前已有有效检查点且状态未变化时，解决 hook 或签名等问题后，可以使用“检查并继续提交”。

## 提示“无法确认 Git 及其子进程已停止”时

这表示程序无法证明本次执行已经结束，例如 Git 主进程先退出，后台子进程仍持有输出管道。此时当前会话暂停写入；如果已取得 Gitviz 操作锁，也会保留它，让其他宿主无法直接接着写入。

1. 保留工作文件，查看报错与操作记录。检查对应仓库的 Git、hook、签名或过滤器进程是否仍在运行。
2. 确认相关进程已结束，再检查 `git status`、HEAD、分支、暂存区和备份引用；不要自动丢弃现场。
3. 仅在确认没有另一个宿主正在写入后，处理遗留的 Gitviz 锁。用 `git rev-parse --git-path gitviz-operation.lock` 查找本 worktree 的路径；不要按固定 `.git/` 路径猜测，也不要批量删除其他 Git 锁。
4. 重新打开宿主后再检查记录。符合检查点要求的失败提交可继续；“进行中或已中断”记录仅供检查，需要按实际 Git 状态处理。

锁只协调 Gitviz，外部 Git 命令不会遵守它。只读命令发生不确定状态时会暂停当前服务的写入，但不会凭空创建写入锁。重新打开应用不能代替检查仍在运行的进程。

## 已验证与限制

Windows 上已验证真实 hook 派生进程的 PID 消失、心跳停止、文件和暂存内容保留，以及修复 hook 后继续提交；已覆盖清理失败时保留锁，以及主进程退出但输出未关闭的有界报错。Rust 与 Node 都有对应测试，插件包内的模块也执行同一组进程测试。

Windows 使用精确进程 PID 的 `taskkill /T /F`；Unix 使用本次创建的独立进程组，Linux/macOS 的真实 Git 后端测试已在 CI 通过，原生界面仍未验收。不能保证捕获主动脱离进程树、关闭继承输出的后台任务，也不能撤销 hook 的外部副作用。插件已通过独立执行进程处理正常关闭和测试宿主 PID 被终止；完整验证范围见 [插件关闭行为](plugin-lifecycle.md)。强杀执行进程或整个进程树、断电和崩溃仍不保证完成。桌面旧 gix 读取和导出不属于本次 Git CLI 超时覆盖范围。

Windows CI 曾出现子进程已停止、但底层清理结果无法确认的偶发失败；保护锁因此保留。现已增加清理错误诊断，本机重复和下一轮 CI 未复现，但尚未确认根因或消除该问题。遇到此提示仍须按上面的检查步骤处理。

设计依据：[Node 子进程文档](https://nodejs.org/api/child_process.html)、[Microsoft taskkill 文档](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/taskkill)。测试入口：`tests/git-process.test.cjs` 与 `src-tauri/src/commands/operations.rs`。
