# 三宿主同仓库并发验收

基线 main / 0ee1c38，工作树干净。本批仅补公开交付 P1 的完整原生并发：Windows 桌面、已安装 VSIX 和 DSH Web 在三个真实界面中打开同一个新建合成仓库；所有目录位于 F 盘 scratch，禁止在用户仓库测试写入。

三轮轮换写入者、锁竞争者和过期确认者，使每个宿主各承担一次角色。三个界面先预览恢复；写入者确认后，真实 pre-commit hook 暂停，锁竞争者确认应被拒绝，不能改变持有者 PID、HEAD/index/工作文件或增加记录。放行 hook 后核对唯一新提交的 parent/tree/backup/clean；再确认第三端的旧预览，应被拒绝且不产生写入。最后三端刷新，实际位置和同一完成记录一致。恢复目标交替使用最早与原 HEAD，确保每轮都有真实内容变化。

测试只点击已有界面控件和正式确认，不模拟宿主消息或替换 Git 服务。用只读 Git 命令、文件哈希和日志核对结果；验证所运行程序/插件来自已核对的 CI 构建。测试结束正常关闭自己的应用、释放 hook，保留可审查证据。若出现产品缺陷，先记录再最小修复并针对失败场景复验；本批不以并发浏览或单后端锁测试替代三宿主真实流程，也不宣称锁能阻止外部 Git。

实测补充：桌面 `Operations::execute` 在取得文件锁之前检查历史 revision；恢复已经创建备份引用时，它会先报“历史已变化”。这也是有效的并发拒绝，但不作为该次请求触达 Rust 文件锁的证据。测试允许桌面这一精确错误分支，仍验证所有状态/记录及持有者锁不变；插件仍须报锁占用。错误文本写入结果。地图节点虚拟化后用实际全历史搜索定位，不假设目标节点始终挂载。

产品缺陷：DSH 完成恢复后，桌面“刷新历史”更新实际 HEAD，但已展开的记录仍显示进行中。地图内部 revision 未进入 App 的记录 refreshKey。改为把实际 repoSnapshot 对象作为记录刷新依赖，每次新的历史快照（包括相同 Git revision）都会重读记录；blocked 的原有变化仍处理本端执行。不能只依赖 HEAD，因为失败/记录完成也可能不改变 HEAD。重建原生桌面并重跑三轮，再核对已展开的同一记录变为完成。
